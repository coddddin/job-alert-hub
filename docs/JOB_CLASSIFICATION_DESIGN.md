# 직무 분류와 민간 출처 확장 설계

상태: 제안 (2026-11-17). 이 문서가 확정되면 아래 순서대로 작은 PR로 구현한다.

## 1. 문제

- 화면의 맞춤 탭·알림은 `kind === 'development'`와 `role`(프론트엔드·백엔드·…·전산·IT)로 판정한다.
- ALIO는 공고에 NCS 직무 코드가 있어 정보통신 직무를 정확히 고른다.
- 잡코리아 공개 상세의 JSON-LD에는 직무 필드가 없다. 지금은 모두 `role: ''`로 들어와
  전체 탭에만 보이고 맞춤·알림에서 빠진다. 표본에는 교육생 모집, 식품·의료 등 비개발 공고가 섞여 있다.
- 수집량을 늘리거나 사람인·원티드를 붙이면, 분류하지 못한 공고가 그만큼 늘어난다.

## 2. 원칙

1. **출처가 준 분류(코드·태그) > 규칙 분류 > 미분류.** 출처 코드가 있으면 그대로 매핑하고 추측하지 않는다.
2. **알림의 오탐이 누락보다 나쁘다.** 규칙이 애매하거나 충돌하면 미분류로 두고 전체 탭에만 보인다.
3. **근거를 남긴다.** 어떤 코드·키워드로 분류했는지 스냅샷에 기록해 화면과 검증에서 확인한다.
4. **유료 서비스 금지.** LLM 분류는 쓰지 않는다. 사전과 규칙은 버전을 붙여 저장소에 둔다.

## 3. 데이터 계약

`CollectedJob`의 `kind`·`role`은 그대로 두어(기존 화면 호환) 아래 필드를 **선택 필드**로 추가한다.

```ts
classification?: {
  method: 'source-code' | 'source-tag' | 'rule' | 'none';
  version: string;            // 'ncs-map/1', 'saramin-code/1', 'keyword-rules/1'
  evidence: readonly string[]; // 예: ['NCS:정보통신', 'title:백엔드', 'skill:Spring']
  nonHiring?: boolean;         // 교육생 모집·광고성 공고
}
```

- `method: 'none'`이면 `role: ''`, `kind: 'other'`. 화면 규칙(전체 탭만)은 지금과 같다.
- 잡코리아 추출기는 분류하지 않고 **신호만** 넘긴다. Python 계약에 `signals`를 선택 필드로 추가한다:
  `{ skills: string[], duties: string | null, jobNames: string[] }`. 추출기 버전은 `jobkorea-detail/2`.
- 판단은 TypeScript 한 곳(`apps/collector/src/classify/`)에서 한다. 출처마다 코드를 해석하는 함수와
  공통 키워드 규칙을 둔다. 세 출처가 같은 함수를 지나므로 결과 기준이 하나다.

```
provider(raw + signals) ─▶ classify(source, signals) ─▶ CollectedJob{kind, role, classification}
   ALIO:     NCS 코드            → ncs-map/1         (기존 로직 이동)
   사람인:   목록의 직무 태그     → saramin-tags/1    (출처 태그)
   원티드:   보류 (7절)
   잡코리아: 제목·스킬·담당업무   → keyword-rules/1   (규칙)
```

## 4. 규칙 분류 (잡코리아용)

- 사전 `apps/collector/src/classify/keyword-rules.v1.json`: 역할별 양성 키워드(예: 백엔드 = Spring, Django,
  Node.js, 서버 개발), 공통 개발 신호(개발자, 엔지니어, SW), 음성 키워드(영업, 생산직, 간호, 조리,
  디자이너(단, UI 개발 제외)), 비채용 신호(교육생 모집, 국비, 수강생, 부트캠프 모집).
- 판정 순서: 비채용 → 음성 우세면 `other` → 역할 키워드가 한 역할에만 있으면 그 역할 → 여러 역할이면
  `풀스택`은 프론트+백엔드 동시일 때만, 나머지는 미분류 → 개발 신호만 있으면 `전산·IT`.
- 제목만으로 결정하지 않고 스킬·담당업무가 같은 방향일 때 확정한다. "직무별 상이" 공고는 미분류.
- 검증: 수집한 공고에서 라벨 표본을 만들고(사람 검토), 사전을 고친 뒤에는 **다른 날짜의 holdout**으로만
  정밀도·재현율을 잰다. 합격 기준: 개발 분류 정밀도 95% 이상. 재현율은 기록만 한다.

## 5. 화면

- 규칙 분류 공고는 맞춤·알림에 포함하되 상세에 `자동 분류 · 근거: …`를 표시한다.
- 출처 태그(공공기관·잡코리아·사람인·원티드)는 이미 있다. 비채용 공고는 전체 탭에서 기본으로 숨기고
  `교육·광고 포함` 체크로 볼 수 있게 한다.

## 6. 수집 확장: 시간 분산과 증분 수집

**차단을 피하려고 IP를 바꾸거나 우회하는 방식은 쓰지 않는다.** 사이트가 막는 요청을 다른 경로로 다시
보내는 것은 그 사이트의 접근 통제를 피하는 일이고, 차단·법적 문제로 서비스 전체가 멈출 수 있다.
대신 요청 수 자체를 줄인다.

1. **증분 수집:** 목록 페이지(요청 적음)로 새 공고 ID만 찾고, 이미 본 ID의 상세는 다시 요청하지 않는다.
   본 공고는 마감일까지 저장소에 유지하고, 마감일이 지나면 뺀다.
2. **시간 분산:** 하루 1회 대신 여러 번(예: 06·12·18시) 나눠 실행하고, 회당 상세 요청 상한(예: 40건)과
   2초 이상 간격을 지킨다. 하루 상한을 넘으면 다음 회차로 미룬다.
3. **차단 신호 존중:** 401·403·429·5xx가 오면 즉시 멈추고 그날은 재시도하지 않는다(현재 동작 유지).
   연속 실패가 있으면 다음 실행 간격을 늘린다.
4. **저장소:** 누적 공고는 `data-store` 브랜치의 `jobkorea.json`에 워크플로가 커밋한다(`contents: write`
   권한을 그 작업에만 부여). 결합 시 "같은 날짜만" 규칙을 "마감 전 + 마지막 확인 7일 이내"로 바꾸고,
   확인 시각은 공고별 `observedAt`로 표시한다.

## 7. 사람인·원티드 (공개 페이지, API 미사용)

사용자 결정(2026-11-17): 공식 API는 쓰지 않는다. 잡코리아와 같이 공개 페이지를 읽되, 6절의 요청 원칙을 따른다.
2026-11-17에 `JobAlertHubValidation/0.2` UA로 각 1~3회 요청해 확인한 결과:

| 출처 | 접근 | 구조 | 분류 신호 | 판단 |
|---|---|---|---|---|
| 사람인 | 검색 `/zf_user/search/recruit` 200, robots.txt에서 검색 경로 허용 | **목록 한 페이지(1요청)에 공고 40건**의 제목·회사·근무지·경력·학력·고용형태·마감·직무 태그 | 사이트가 붙인 직무 태그(`job_sector`, 예: "반도체설계, 공정엔지니어") | 진행. 상세 요청 없이 목록만으로 수집 |
| 원티드 | 목록 `/wdlist` 200이지만 공고는 브라우저에서 내부 JSON으로 그린다. robots.txt·sitemap은 우리 UA에 CloudFront 403 | 서버 HTML에 공고 없음 | (확인 불가) | **보류.** 공개 HTML에 데이터가 없고 자동 접근을 거부하는 신호가 있다. UA 위장·내부 JSON 호출은 하지 않는다 |

- 사람인 상세(`/zf_user/jobs/relay/view`)는 본문이 비동기로 로드되고 JSON-LD가 없어, 목록 정보만 쓴다.
  상세 링크는 원문 이동용으로 화면에 둔다.
- 사람인 직무 태그는 사이트 분류어이므로 `method: 'source-code'`가 아닌 `'source-tag'`로 기록하고,
  태그→역할 매핑 사전(`saramin-tags/1`)으로 분류한다. 키워드 규칙보다 우선한다.
- 사람인 수집은 검색어(개발·프론트엔드·백엔드 등)별 목록 페이지를 2초 간격으로 읽고 회당 상한 10페이지(최대 400건).
  ID는 `saramin:<rec_idx>`. 403·429·5xx면 그 회차를 멈춘다.

## 8. 직무 추정 모델 (직무를 모르는 공고)

규칙으로도 정하지 못한 공고의 직무군을 **추정**한다. 유료 서비스·LLM은 쓰지 않는다.

### 8.1 계층

`출처 코드 > 출처 태그 > 규칙 > 모델 > 미분류`. 규칙과 모델이 다르면 미분류. 모델 결과는
`classification.method: 'model'`, `version: 'family-model/<n>'`, 근거는 점수가 큰 글자 조각, 신뢰도는 `confidence`(0~1).

### 8.2 학습 데이터: 이미 라벨이 있는 출처로 라벨 없는 출처를 배운다(약지도)

| 데이터 | 라벨 | 용도 |
|---|---|---|
| ALIO | NCS → 직무군 (출처 코드) | 학습. 공공·의료 편중이라 직무군별 상한을 두고 섞는다 |
| 사람인 | 사이트 직무 태그 → 직무군 (출처 태그) | **학습의 중심.** 잡코리아와 같은 민간 공고 분포 |
| 잡코리아 사람 라벨(2단계에서 작성) | 사람 판정 | **학습에 쓰지 않는다.** 임계값 결정과 평가 전용(gold) |

- 입력은 잡코리아에도 있는 필드만 쓴다: 제목 + 회사명 + (있으면) 스킬·담당업무. 사람인 태그는 라벨이므로 입력에 넣지 않는다.
- 규칙·모델이 스스로 붙인 라벨로 다시 학습하지 않는다(오류 증폭 방지).

### 8.3 모델

- 글자 2~4-gram TF-IDF + 직무군별 로지스틱 회귀(one-vs-rest, 다중 라벨), 직무군 가중치 균형.
- 이유: 한국어 형태소 분석기 없이 동작, 적은 데이터·CPU 수 초 학습, 결정적, 가중치로 근거(어떤 글자 조각 때문인지)를 보여 줄 수 있다.
- 다음 후보(v2, 필요할 때만): 무료 공개 다국어 문장 임베딩 소형 모델 + 같은 분류기. CPU로 가능하지만 의존성이 크다.

### 8.4 받아들이는 기준

- 직무군마다 gold에서 정밀도가 목표(IT 95%, 그 외 90%) 이상이 되는 최소 확률을 임계값으로 정한다.
- gold 표본이 10건 미만인 직무군은 자동 배정하지 않는다(미분류 유지).
- 최고 확률이 임계값 미만이면 미분류. 화면에서는 기존처럼 확인 필요에 남는다.

### 8.5 실행 위치

- 학습: `tools/classifier/train.py`(Python, scikit-learn). 누적 저장소(6절)의 최근 N일 데이터로 주 1회 또는 수동 실행.
  산출물 `apps/collector/src/classify/family-model.v<n>.json`(직무군별 상위 n-gram 가중치·임계값, 수백 KB)과
  평가 보고서(직무군별 정밀도·재현율·커버리지)를 커밋한다.
- 추론: TypeScript(`classify/model.ts`)에서 같은 n-gram·가중치로 계산한다. 수집기 실행에 Python이 필요 없다.
  Python과 TS 점수가 같은지 고정 예제 1개로 확인한다.

### 8.6 화면·알림

- 상세: `자동 추정 · 근거: ‘간호’, ‘병동’ · 신뢰도 92%`.
- 맞춤 탭에는 포함, **알림에는 넣지 않는다**(규칙·출처 분류만 알림). 모델 정밀도가 실제 운영에서 확인되면 다시 결정한다.
- 수집 요약에 미분류 비율과 추정 직무군 분포를 남겨, 분포가 크게 바뀌면 재학습한다.

### 8.7 2026-11-17 타당성 실험 (ALIO만으로 학습)

- 학습: 배포 ALIO 중 직무군 1개인 414건(의료 277, 연구 40, 사무 39, 서비스 23, 물류 16, IT 11 …).
- ALIO 5겹 교차검증: 정확도 0.80. 의료 0.95, 물류 0.88, IT 0.86이나 사무 0.38, 연구 0.56, 서비스 0.43.
- 잡코리아 38건에 적용: **최고 확률이 모두 0.49 이하**, 대부분 ‘의료’로 기울었다(피부관리사 외 조리·영업·무역도 의료).
- 결론: 공공·의료 편중 데이터만으로는 민간 공고를 추정할 수 없다. 사람인 태그 데이터와 직무군별 상한이 필수이고,
  임계값이 없으면 오분류가 그대로 노출된다. 낮은 확률을 미분류로 남기는 8.4 기준이 이 실험에서는 모두 미분류로 처리해 안전했다.

## 9. 공고 유형 피처 (직무군과 별개의 축)

직무군은 "무슨 일"이고, 공고 유형은 "어떤 자리"다. 같은 IT 공고도 정규직·체험형 인턴·육아휴직 대체·장애인 전형이
섞여 있어 사용자가 원하는 것과 다를 수 있다. 직무군 분류와 독립된 피처로 둔다.

### 9.1 실제 공고 조사 (2026-11-17)

배포 ALIO 508건(구조화 필드 + 제목), 잡코리아 38건(제목·경력 원문), 사람인 목록 40건(근무 조건 원문)을 훑었다.

| 주의 표시 | 잡코리아: 고수익 강조 3(‘고졸이 월 900’, ‘월490이상’, ‘연4600’), 해외 근무 6(베트남·일본) | 제목 |

함정:
- ‘인턴’ ≠ 인턴십: `전공의(인턴)`, `수련생(체험형 청년인턴)`처럼 의료 수련·실습이 섞인다.
- ‘지사’ ≠ 가맹 모집: ALIO의 `경북지사`, `대구지역본부`는 근무지다. ‘사업점 모집’, ‘가맹’, ‘대리점 개설’만 사업자 모집.
- ‘개발’ ≠ IT: 사람인 ‘개발’ 검색에 ‘부동산 개발’, ‘재개발 현장 보건관리자’, ‘영어교재 개발’이 섞인다(직무군 규칙도 같은 함정).
- 연봉·월급 숫자 자체는 정상 정보다. ‘월 900’, ‘투자비 없는’처럼 **고수익 강조 + 경력무관 + 영업·육성반** 조합만 주의 표시.

### 9.2 데이터 계약

`CollectedJob.postingType`(선택 필드, `version: 'posting-type/1'`):

```ts
postingType?: {
  nature: 'hiring' | 'training' | 'business';          // training·business면 채용 아님
  employment: readonly ('regular' | 'indefinite' | 'contract' | 'part-time' | 'dispatch' | 'freelance' | 'intern')[];
  intern: 'experience' | 'conversion' | 'student' | null; // 체험형 / 채용연계·전환형 / 대학생 방학 인턴
  replacement: boolean;                                    // 휴직·육아휴직 대체
  eligibility: readonly ('disability' | 'veteran' | 'high-school' | 'local' | 'youth' | 'social-equity')[];
  track: 'open' | 'rolling' | 'urgent' | null;
  flags: readonly ('overseas' | 'incentive-heavy' | 'headhunting' | 'medical-residency')[];
  evidence: readonly string[];                             // 예: ['ALIO:청년인턴(체험형)', 'title:장애전형']
}
```

- `classification.nonHiring`은 `nature !== 'hiring'`에서 파생한다(한 곳에서 판단).
- 우선순위: 출처 구조화 필드(ALIO 고용형태·대체인력, 사람인 근무 조건, 잡코리아 JSON-LD) > 제목·본문 규칙 사전
  `posting-type-rules.v1.json`. 둘이 다르면 구조화 필드를 따르고 근거에 둘 다 남긴다.
- 직무군과 달리 모델 추정은 하지 않는다. 표현이 정형적이라 규칙으로 충분하고, 잘못 숨기는 비용이 크다.

### 9.3 판정 규칙의 보수성

- `nature: training/business`(채용 아님 → 기본 숨김)는 **강한 표현 1개 이상 + 반대 신호 없음**일 때만. 예: ‘교육생 모집’, ‘국비’, ‘수강생’, ‘사업점 모집’.
  ‘채용’, ‘정규직’, ‘연봉’과 함께 있으면(예: ‘채용연계형 교육생’) `hiring` + `intern: conversion` 후보로 두고 확인 필요.
- `medical-residency`: ‘전공의’, ‘수련의’가 있으면 인턴 유형으로 세지 않는다.
- 대상 제한 전형은 숨기지 않고 태그로 보여 준다.

### 9.4 화면·질문·맞춤

- 목록 행에 짧은 유형 태그: `체험형 인턴`, `계약직`, `대체인력`, `장애인 전형`, `해외 근무`, `고수익 강조 주의`.
- 필터 막대에 ‘근무 형태’(정규직 / 계약·기간제 포함 / 인턴 포함 / 시간제 포함).
- 첫 방문 질문에 선택 문항 추가:
  - “어떤 자리를 찾으세요?” 정규직만 / 계약직도 / 인턴·체험형도(복수). 기본값: 신입은 인턴 포함, 경력은 인턴 제외.
  - “해당하면 고르세요(선택)” 장애인·보훈·고졸 전형. 민감 정보이므로 **이 브라우저에만 저장**하고, 고르지 않아도 된다고 명시.
- 맞춤 판정: 원하지 않은 근무 형태 → 제외(이유 표시). 대상 제한 전형인데 해당 표시가 없으면 확인 필요(‘장애인 전형 · 대상자만 지원’).
  채용 아님 → 제외(전체 탭에서는 ‘교육·광고 포함’ 체크 시 보임). 주의 표시는 판정에 영향 없이 태그만.
- 알림: 맞춤과 같되 `incentive-heavy` 공고는 제외.

### 9.5 검증

- 출처별 150건 이상 사람 라벨(유형 축마다)로 정밀도를 잰다. 목표: 채용 아님 판정 정밀도 98% 이상(잘못 숨기면 진짜 공고를 놓친다),
  고용 형태·인턴 유형·대체 인력 95% 이상. 규칙을 고친 표본과 다른 날짜의 holdout으로만 잰다.
- 함정 사례(전공의 인턴, ○○지사, 부동산 개발, 채용연계형 교육생)는 고정 단위 테스트로 남긴다.

## 10. 취향에 맞춘 수집 우선순위

사용자의 관심 직무에 맞춰 수집량을 조절한다. 단, **사용자별 크롤링은 하지 않는다.**
정적 사이트라 서버가 개인의 답을 모르고(브라우저에만 저장), 사용자 수만큼 요청이 늘면 차단 위험이 커진다.

1. **직무군별 수집 예산:** 출처 회당 요청 상한(사람인 10페이지, 잡코리아 상세 40건)을 직무군에 나눈다.
   기본은 고르게, 최근 7일 공고가 적은 직무군에 더 배정한다(최소 1, 최대 3배). 설정은 `tools/public-jobs/collection-plan.json`
   (`{ family: { saraminQueries: [...], weight } }`)에 두고 사이트 주인이 조정한다. 수집 요약에 직무군별 공고 수를 남긴다.
2. **크롤링 없는 보완:** 내 관심 직무의 맞춤 공고가 적으면(예: 5건 미만) 첫 방문 답을 그대로 담은
   "사람인·잡코리아에서 같은 조건으로 더 보기" 링크를 보여 준다(기존 `site-links.js` 확장, 요청 0).
3. **집계 수요 반영(로그인이 생긴 뒤):** 개인이 아닌 직무군별 관심 **합계**만 받아 1번 가중치에 반영한다.
   개인 답은 서버에 저장하지 않는다.

## 11. 구현 순서

1. 분류 모듈과 계약 필드 추가, ALIO NCS 매핑을 이 모듈로 이동(동작 동일 확인).
2. 잡코리아 추출기 `signals` + 키워드 규칙 v1 + 라벨 표본·holdout 평가.
3. 비채용 판정과 화면(자동 분류 근거, 교육·광고 토글).
4. 사람인 목록 수집기(Python 추출 → 같은 JSON 계약 v1의 `source: 'saramin'`) + 태그 매핑.
5. 원티드: 공개 HTML에 데이터가 생기거나 접근 거부가 풀리면 재검토.
6. 잡코리아 증분 저장소와 하루 여러 번 실행.
7. 직무 추정 모델(8절): 사람인 수집 데이터와 잡코리아 gold가 생긴 뒤 학습·평가 → TS 추론 → 화면 연결.
8. 공고 유형 피처(9절): 계약·규칙 사전·출처 구조화 필드 매핑 → 유형 태그·필터 → 첫 방문 선택 문항 → 맞춤·알림 반영.
9. 수집 우선순위(10절): 직무군별 예산 설정 → 적을 때 같은 조건 더 보기 링크.

각 단계는 기존 한 번의 브라우저 통합 흐름(`tools/public-jobs/verify-front.mjs`)에 출처·분류 확인을 더해 검증한다.
