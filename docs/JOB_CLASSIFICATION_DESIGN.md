# 직무 분류와 민간 출처 확장 설계

상태: 제안 (2026-11-17). 이 문서가 확정되면 아래 순서대로 작은 PR로 구현한다.

## 1. 문제

- 화면의 맞춤 탭·알림은 `kind === 'development'`와 `role`(프론트엔드·백엔드·…·전산·IT)로 판정한다.
- ALIO는 공고에 NCS 직무 코드가 있어 정보통신 직무를 정확히 고른다.
- 잡코리아 공개 상세의 JSON-LD에는 직무 필드가 없다. 지금은 모두 `role: ''`로 들어와
  전체 탭에만 보이고 맞춤·알림에서 빠진다. 표본에는 교육생 모집, 식품·의료 등 비개발 공고가 섞여 있다.
- 수집량을 늘리거나 사람인·원티드를 붙이면, 분류하지 못한 공고가 그만큼 늘어난다.

## 2. 원칙

1. **출처가 준 분류 > 규칙 분류 > 미분류.** 출처 코드가 있으면 그대로 매핑하고 추측하지 않는다.
2. **알림의 오탐이 누락보다 나쁘다.** 규칙이 애매하거나 충돌하면 미분류로 두고 전체 탭에만 보인다.
3. **근거를 남긴다.** 어떤 코드·키워드로 분류했는지 스냅샷에 기록해 화면과 검증에서 확인한다.
4. **유료 서비스 금지.** LLM 분류는 쓰지 않는다. 사전과 규칙은 버전을 붙여 저장소에 둔다.

## 3. 데이터 계약

`CollectedJob`의 `kind`·`role`은 그대로 두어(기존 화면 호환) 아래 필드를 **선택 필드**로 추가한다.

```ts
classification?: {
  method: 'source-code' | 'rule' | 'none';
  version: string;            // 'ncs-map/1', 'saramin-code/1', 'keyword-rules/1'
  evidence: readonly string[]; // 예: ['NCS:정보통신', 'title:백엔드', 'skill:Spring']
  nonHiring?: boolean;         // 교육생 모집·광고성 공고
}
```

- `method: 'none'`이면 `role: ''`, `kind: 'other'`. 화면 규칙(전체 탭만)은 지금과 같다.
- 잡코리아 추출기는 분류하지 않고 **신호만** 넘긴다. Python 계약에 `signals`를 선택 필드로 추가한다:
  `{ skills: string[], duties: string | null, jobNames: string[] }`. 추출기 버전은 `jobkorea-detail/2`.
- 판단은 TypeScript 한 곳(`apps/collector/src/classify/`)에서 한다. 출처마다 코드를 해석하는 함수와
  공통 키워드 규칙을 둔다. 세 출처가 같은 함수를 지나므로 결과 기준이 하나다.

```
provider(raw + signals) ─▶ classify(source, signals) ─▶ CollectedJob{kind, role, classification}
   ALIO:     NCS 코드            → ncs-map/1         (기존 로직 이동)
   사람인:   job_mid_cd/job_cd   → saramin-code/1    (출처 코드)
   원티드:   category/tag id     → wanted-code/1     (출처 코드)
   잡코리아: 제목·스킬·담당업무   → keyword-rules/1   (규칙)
```

## 4. 규칙 분류 (잡코리아용)

- 사전 `apps/collector/src/classify/keyword-rules.v1.json`: 역할별 양성 키워드(예: 백엔드 = Spring, Django,
  Node.js, 서버 개발), 공통 개발 신호(개발자, 엔지니어, SW), 음성 키워드(영업, 생산직, 간호, 조리,
  디자이너(단, UI 개발 제외)), 비채용 신호(교육생 모집, 국비, 수강생, 부트캠프 모집).
- 판정 순서: 비채용 → 음성 우세면 `other` → 역할 키워드가 한 역할에만 있으면 그 역할 → 여러 역할이면
  `풀스택`은 프론트+백엔드 동시일 때만, 나머지는 미분류 → 개발 신호만 있으면 `전산·IT`.
- 제목만으로 결정하지 않고 스킬·담당업무가 같은 방향일 때 확정한다. "직무별 상이" 공고는 미분류.
- 검증: 수집한 공고에서 라벨 표본을 만들고(사람 검토), 사전을 고친 뒤에는 **다른 날짜의 holdout**으로만
  정밀도·재현율을 잰다. 합격 기준: 개발 분류 정밀도 95% 이상. 재현율은 기록만 한다.

## 5. 화면

- 규칙 분류 공고는 맞춤·알림에 포함하되 상세에 `자동 분류 · 근거: …`를 표시한다.
- 출처 태그(공공기관·잡코리아·사람인·원티드)는 이미 있다. 비채용 공고는 전체 탭에서 기본으로 숨기고
  `교육·광고 포함` 체크로 볼 수 있게 한다.

## 6. 수집 확장: 시간 분산과 증분 수집

**차단을 피하려고 IP를 바꾸거나 우회하는 방식은 쓰지 않는다.** 사이트가 막는 요청을 다른 경로로 다시
보내는 것은 그 사이트의 접근 통제를 피하는 일이고, 차단·법적 문제로 서비스 전체가 멈출 수 있다.
대신 요청 수 자체를 줄인다.

1. **증분 수집:** 목록 페이지(요청 적음)로 새 공고 ID만 찾고, 이미 본 ID의 상세는 다시 요청하지 않는다.
   본 공고는 마감일까지 저장소에 유지하고, 마감일이 지나면 뺀다.
2. **시간 분산:** 하루 1회 대신 여러 번(예: 06·12·18시) 나눠 실행하고, 회당 상세 요청 상한(예: 40건)과
   2초 이상 간격을 지킨다. 하루 상한을 넘으면 다음 회차로 미룬다.
3. **차단 신호 존중:** 401·403·429·5xx가 오면 즉시 멈추고 그날은 재시도하지 않는다(현재 동작 유지).
   연속 실패가 있으면 다음 실행 간격을 늘린다.
4. **저장소:** 누적 공고는 `data-store` 브랜치의 `jobkorea.json`에 워크플로가 커밋한다(`contents: write`
   권한을 그 작업에만 부여). 결합 시 "같은 날짜만" 규칙을 "마감 전 + 마지막 확인 7일 이내"로 바꾸고,
   확인 시각은 공고별 `observedAt`로 표시한다.

## 7. 사람인·원티드

공개 페이지를 긁지 않고 **공식 API**를 쓴다. 출처 코드로 분류할 수 있어 규칙 분류보다 정확하고,
차단 위험이 없다.

| 출처 | 경로 | 분류 신호 | 필요한 것 |
|---|---|---|---|
| 사람인 | 사람인 채용공고 Open API (`oapi.saramin.co.kr`) | 직무 코드(job_mid_cd, job_cd) | 무료 access-key 발급 → GitHub secret `SARAMIN_KEY` |
| 원티드 | 원티드 OpenAPI (`openapi.wanted.jobs`) | 직군·직무 카테고리 | 파트너 신청 후 client id/secret → secret 2개 |

- 일일 호출 한도·약관·표시 의무(출처 표기, 링크)는 키 발급 시 확인해 이 표에 적는다.
- 구현은 ALIO와 같은 TypeScript Provider. 키가 없거나 실패하면 그 출처만 빠지고 나머지는 배포된다
  (잡코리아 결합과 같은 선택 단계).

## 8. 구현 순서

1. 분류 모듈과 계약 필드 추가, ALIO NCS 매핑을 이 모듈로 이동(동작 동일 확인).
2. 잡코리아 추출기 `signals` + 키워드 규칙 v1 + 라벨 표본·holdout 평가.
3. 비채용 판정과 화면(자동 분류 근거, 교육·광고 토글).
4. 사람인 API Provider(키 발급 후). 5. 원티드 API Provider(파트너 승인 후).
6. 잡코리아 증분 저장소와 하루 여러 번 실행.

각 단계는 기존 한 번의 브라우저 통합 흐름(`tools/public-jobs/verify-front.mjs`)에 출처·분류 확인을 더해 검증한다.
