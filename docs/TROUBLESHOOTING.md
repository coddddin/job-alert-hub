## 1. 가상 데이터로는 통과, 실데이터 해석률 63.3%

**상황.** 가상 공고 12건으로 만든 파서의 테스트는 모두 통과했습니다. 그런데 공공데이터포털의 실제 공고 519건에 처음 돌리자, 마감일은 **한 건도** 해석하지 못했고 근무지는 53건을 해석하지 못했습니다.

**원인.**
- API가 마감일을 `20261117`처럼 구분자 없이 줬습니다. 파서는 `2026.11.17`, `~11/17` 같은 형식만 알았습니다.
- 근무지에 `전남광주`가 있었습니다. 2026년 7월 광주광역시와 전라남도가 합쳐져 생긴 이름인데, 파서는 기존 17개 시·도만 알았습니다.

**해결.**
- `YYYYMMDD` 형식을 추가했습니다. 전화번호 같은 8자리 숫자를 날짜로 오해하지 않도록 19xx·20xx년으로 시작할 때만 인정합니다.
- `전남광주`를 18번째 시·도로 추가하지 않고, `광주`·`전남` 두 곳으로 해석했습니다. 새 값을 추가하면 사용자가 저장해 둔 `광주` 필터가 통합 명칭 공고와 맞지 않게 되기 때문입니다. 뒤에 `광산구`가 오면 광주, `화순군`이 오면 전남으로 되짚습니다.
- 실제 표기를 그대로 테스트 케이스로 고정했습니다. 해석률은 63.3%에서 99.9%가 되었습니다.

**배운 점.** 가상 데이터는 내가 상상한 표기만 검증합니다. 그래서 매일 수집할 때마다 해석률과 "해석하지 못한 원문 상위 10개"를 자동으로 남기도록 했습니다. 다음에 추가할 규칙은 추측이 아니라 이 목록에서 고릅니다.

## 2. 원문을 인자로 줬는데 CLI가 끝나지 않음

**상황.** `kr-job-parser exp "경력 3년↑"`가 결과를 출력하고도 종료되지 않고 멈춰 있었습니다.

**원인.** CLI는 원문을 인자로 받거나, 파이프로 여러 줄을 받습니다. 시작할 때 표준 입력이 터미널이 아니면 무조건 `readline`을 열었는데, 열린 입력 스트림이 있으면 Node.js는 입력이 끝날 때(EOF)까지 이벤트 루프를 유지합니다. 인자로 원문을 받아 표준 입력을 쓰지 않는 경우에도 프로세스가 끝나지 않았습니다.

**해결.** 표준 입력을 값이 아니라 "여는 함수"로 넘기고, 원문 인자가 없을 때만 열게 바꿨습니다. 그리고 빌드한 결과물을 **실제 프로세스로 실행하는 테스트**를 추가해, 같은 문제가 다시 생기면 테스트가 시간 초과로 실패하게 했습니다.

**배운 점.** 단위 테스트는 가짜 입출력을 쓰기 때문에 이 문제를 잡지 못했습니다. 프로세스 수명처럼 실행 환경에 달린 문제는 실제로 실행하는 테스트가 필요합니다.

→ [bada4f5](https://github.com/coddddin/job-alert-hub/commit/bada4f5) · [run.ts](../packages/kr-job-parser/src/cli/run.ts) · [cli.test.ts](../packages/kr-job-parser/test/cli.test.ts)

## 3. 로컬은 통과, CI는 실패

**상황.** 로컬에서 `pnpm check`는 통과했는데, PR의 CI는 Node 22·24 모두 실패했습니다.

**원인.** CI 로그를 보니 수집기의 린트가 `kr-job-parser`의 타입을 찾지 못하고 있었습니다. 수집기는 파서를 빌드한 결과물(`dist/*.d.ts`)에서 타입을 읽는데, CI는 빌드보다 린트를 먼저 돌렸습니다. 로컬에는 예전에 빌드한 `dist`가 남아 있어서 문제가 가려졌습니다.

**해결.** 저장소를 새로 클론한 폴더에서 같은 실패를 재현한 다음, CI와 `pnpm check` 모두 빌드를 먼저 하도록 순서를 바꿨습니다.

**배운 점.** "내 컴퓨터에선 된다"의 원인은 대개 남아 있는 상태입니다. 고치기 전에 깨끗한 환경에서 먼저 재현합니다. 더 근본적으로는 TypeScript project references로 빌드 결과물 없이 타입을 읽게 할 수 있어, 개선 과제로 남겨 두었습니다.

→ [1365467](https://github.com/coddddin/job-alert-hub/commit/1365467)

## 4. API 인증키가 "등록되지 않음"으로 거절됨

**상황.** GitHub Secrets에 등록한 공공데이터포털 키로 요청하자 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`가 돌아왔습니다.

**원인.** 키 값은 로그에 남길 수 없어서, 키 대신 **형태만** 기록했습니다. 길이, 퍼센트 인코딩 여부, `+ / =` 포함 여부입니다. 길이가 65자였는데, 정상 키는 64자입니다. 등록할 때 끝에 줄바꿈이 함께 들어갔습니다.

**해결.** 수집기가 키의 앞뒤 공백과 줄바꿈을 잘라내도록 했습니다. 키 오류는 코드(`MISSING_KEY`, `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`)로 구분해 알리고, 요청 URL에는 키가 들어 있으므로 오류 메시지에 넣지 않습니다.

**배운 점.** 비밀 값도 노출하지 않으면서 진단할 수 있습니다. 그리고 사람이 다시 실수해도 동작하도록 입력을 정리하는 쪽이, 다시 붙여넣으라고 안내하는 것보다 오래갑니다.

## 5. 정규식이 "이하"를 "이상"으로, "재택 가능"을 "완전 재택"으로 읽음

**상황.** 표 형식 테스트에 사례를 추가하다가 두 가지가 실패했습니다.
- `경력 5년 이하`를 "5년 **이상**"으로 해석했습니다.
- `재택근무 가능`을 "완전 재택"으로 해석했습니다.

**원인.**
- `경력 N년`(하한으로 해석하는 규칙)이 `경력 5년 이하` 안에서도 일치했습니다.
- "재택 병행" 규칙이 `재택 가능`만 알고 `재택근무 가능`은 몰라서, 더 넓은 "완전 재택" 규칙이 먼저 일치했습니다.

**해결.**
- `경력 N년` 규칙은 이상·이하 표기가 없을 때만 쓰도록 했습니다.
- "재택 병행" 규칙이 `근무`를 선택적으로 받도록 고쳤습니다.

**배운 점.** 정규식은 규칙끼리의 우선순위에서 틀립니다. 그래서 입력과 기대값을 표로 나열하는 테스트를 기본으로 씁니다. 사례 하나를 추가하는 비용이 한 줄이라, 의심 가는 표기를 바로 넣어 볼 수 있습니다.

→ [experience.ts](../packages/kr-job-parser/src/experience.ts) · [experience.test.ts](../packages/kr-job-parser/test/experience.test.ts) · [location.test.ts](../packages/kr-job-parser/test/location.test.ts)

## 6. 지표 이름이 실제보다 좋아 보였음

**상황.** 화면과 README에 "해석 성공률 99.9%"라고 적었습니다.

**원인.** 이 값은 "해석하지 못함(`unknown`)이 아닌 비율"입니다. 5번처럼 틀리게 해석해도 해석된 것으로 셉니다. "성공"이라는 이름 때문에 정확도로 읽힐 수 있었습니다.

**해결.** 이름을 "해석률"로 바꾸고, 화면과 README에 정확도가 아니라는 설명을 붙였습니다. 정답을 직접 단 공고 표본으로 정확도를 따로 재는 것을 다음 작업으로 잡았습니다.

**배운 점.** 지표는 무엇을 세는지가 이름에 드러나야 합니다. 좋아 보이는 숫자일수록 무엇을 빼고 셌는지 먼저 확인합니다.

## 7. 민간 사이트 표기 "외 1"을 숨은 근무지 0곳으로 읽음

**상황.** 공공 API로만 검증한 파서를 잡코리아 검색 화면의 실제 표기에 처음 돌렸습니다. 공고를 가져올 수 없어서, 사용자 브라우저 안에서 화면을 읽는 북마클릿으로 돌렸습니다. `서울 구로구 외 1`이 `others: 0`으로 나왔습니다.

**원인.** 숨은 근무지 규칙이 `외 2곳`, `외 3개 지역`처럼 **단위가 붙은** 형태만 알았습니다. 공공 API에는 단위 없는 표기가 없었고, 잡코리아 목록은 단위 없이 `외 1`로 씁니다. 그 결과 다른 지역 필터에서도 "외 1"의 숨은 근무지를 무시하고 바로 제외했습니다. "확인 필요"로 남겨야 할 공고였습니다.

**해결.** 단위가 없어도 숫자 뒤가 문장 끝이거나 구분자일 때는 근무지 수로 읽도록 고쳤습니다. `외 1명` 같은 다른 뜻은 여전히 걸리지 않습니다. 실제 표기를 테스트로 고정하고 kr-job-parser 0.4.1로 내보냈습니다.

**배운 점.** 해석률은 99.9%였지만 이 버그는 해석률에 잡히지 않았습니다. 틀리게라도 "해석됨"으로 셌기 때문입니다(6번과 같은 이유). 데이터 출처가 하나뿐이면 그 출처의 표기 습관까지만 검증됩니다. 그래서 북마클릿에 "틀렸어요" 신고를 넣어, 수집할 수 없는 사이트의 표기도 정확도 셋으로 모이게 했습니다.

## 8. 잡코리아 바로가기의 "분야 전체"가 0건

**상황.** 우리 필터를 다른 사이트 검색 주소로 옮기는 바로가기를 만들고, 프론트엔드·백엔드 같은 개별 분야는 잡코리아에서 직접 열어 확인했습니다. 북마클릿을 만들다가 분야를 "전체"로 둔 링크를 처음 열었더니 결과가 0건이었습니다.

**원인.** 잡코리아 화면에서 대분류 'AI·개발·데이터'의 코드(`10031`)를 그대로 `duty`에 넣었습니다. 잡코리아는 `duty`에 소분류 코드만 받고, 대분류 코드는 빈 결과를 돌려줍니다. 테스트는 "주소가 기대한 문자열과 같은가"만 확인했기 때문에 통과했습니다.

**해결.** 분야 전체일 때는 소분류 18개를 모두 넣도록 바꿨습니다(1,256건 확인). 대분류 코드가 다시 들어가지 않도록 테스트로 고정했습니다.

**배운 점.** 남의 시스템에 넘기는 값은 내 테스트가 아니라 그 시스템이 정답을 정합니다. 문자열 비교 테스트는 형식만 지켜 주므로, 조합마다 실제로 한 번은 열어 봐야 합니다. 바뀔 수 있는 외부 계약이라 [site-links.js](../apps/web/lib/site-links.js)에 확인한 날짜(2026-11)를 적어 두었습니다.
