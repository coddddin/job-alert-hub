# 채용공고 수집·맞춤 알림 프로그램 설계 v0.2

작성일: 2026-09-29. 상태: 사용자 검토 개선안 승인·반영 완료. 실제 사이트 연결·배포·발송은 아직 수행하지 않았다.

구현 현황: [로컬 프로토타입 v0.1](PROTOTYPE.md)에 샘플 목록·필터·스크랩·지원 상태·독립 알림 설정을 구현했다. 이 문서의 나머지 항목은 제품 목표 설계이며 전체 구현 완료를 뜻하지 않는다. 현재 프로토타입은 Node.js와 브라우저 JavaScript를 사용하며 Next.js·TypeScript·DB는 후속 단계다.

## 1. 제품 목표와 기본 가정

여러 채용 사이트에서 제공받은 공고를 한 화면에 모으고, 사용자가 저장한 직무·지역·경력 조건에 맞는 새 공고를 이메일과 휴대폰으로 알린다. 지원은 원문 사이트에서 진행한다.

사용자 결정: 개인용으로 시작하고 나중에 서비스로 확장한다. PC와 휴대폰에서 같은 서비스를 사용하고 홈 화면에 설치할 수 있는 PWA를 우선한다. 첫 버전 알림은 이메일 + 메신저이며 카카오톡을 우선 검토한다. 웹 푸시는 보조 후보로 둔다.

핵심 지표는 수집 성공률, 조건 일치 정확도, 중복 알림률, 마지막 성공 수집 시각, 발견부터 알림 제공업체 접수까지의 지연이다. 공급자가 제공하지 않은 공고의 완전 수집과 게시 즉시 감지는 보장하지 않는다.

## 2. 데이터 확보: 먼저 해결할 의존성

아래는 공식 안내 확인 결과다. 실제 승인 조건과 제공 범위는 신청 시 다시 확인한다.

## 3. 첫 버전 사용자 흐름

1. Google 로그인 후 알림 수신 이메일 확인.
2. 관심 조건 저장: 직무, 포함/제외 키워드, 경력, 지역, 고용형태, 원격근무, 연봉, 학력, 관심/제외 기업.
3. 조건에 맞는 기존 공고 미리보기로 검색 범위 확인.
4. 목록과 별도로 알림 조건을 설정하고 채널·빈도·방해금지 시간 설정.
5. 통합 피드에서 공고를 읽고 저장·관심 없음·지원 상태를 관리.
6. 알림 또는 카드에서 원문으로 이동해 지원.

필수 화면은 통합 공고 피드, 저장 검색 관리, 스크랩/지원 상태, 알림 설정과 이력이다. 운영 화면에는 소스 연결 상태, 마지막 성공 수집 시각, 호출 예산, 오류와 재시도 상태를 표시한다. 예시 데이터와 실제 수집 데이터를 명확히 구분한다.

공고 카드에는 회사·제목·직무·지역·경력·마감일·출처·원문 링크·조건 일치 이유를 표시한다. 미제공 정보는 추정하지 않고 ‘정보 없음’으로 표시한다.

### 승인된 추가 기능

- 목록은 서울 신입 개발자를 넓게 보여주고 알림은 관심 분야와 경력 유형을 별도로 선택한다. 목록 필터 변경으로 알림 조건이 자동 변경되지 않는다.
- 지원 가능성(확인된 필수 조건 충족 여부)과 관심도(선호 분야·기술 일치)를 별도로 표시한다. 사용자 학력 등 필요한 정보가 없으면 전체 지원 자격을 충족한다고 단정하지 않는다. 관심도가 낮아도 지원 가능한 공고를 자동 숨기지 않는다.
- ‘관심 없음’은 분야 불일치·경력 불일치·교육 광고·기업 제외 등의 사유를 기록한다. 기본 효과는 해당 공고 숨김이며, 기업/분야 전체 제외는 사용자가 명시적으로 선택할 때만 규칙으로 반영한다. 규칙 조회와 취소를 제공한다.
- 지원 상태는 검토 중 → 지원 예정 → 지원 완료 → 결과로 관리한다. 결과는 합격·불합격·지원 철회 등을 사용자가 기록하며 원문 방문만으로 지원 완료 처리하지 않는다.
- 스크랩 공고의 마감 임박 및 중요한 조건 변경 알림을 선택적으로 제공한다. 신규 알림과 별도로 켜고 끌 수 있다.

## 4. 검색과 직무 매칭

사이트별 직무 코드를 내부 공통 분류에 매핑하되 원본 코드를 함께 보관한다. 초기 분류는 사용자의 관심 직무부터 구축하며 매핑 버전을 기록한다.

- 같은 항목의 다중 선택은 OR, 서로 다른 항목은 AND로 결합한다.
- 제외 키워드와 제외 기업을 먼저 적용한다.
- 필수 키워드(모두 포함), 선택 키워드(하나 이상), 동의어를 구분한다.
- 경력 범위는 구간 교집합으로 판단하고 ‘경력무관’을 별도 처리한다.
- 연봉·원격근무 등 미상 필드는 사용자가 ‘미상 포함’을 선택할 수 있다.
- 키워드 검색 대상은 제공받은 제목·직무·본문 필드로 제한하며 없는 본문은 검색한 것처럼 취급하지 않는다.

### 사용자 기본 검색: 서울 신입 개발자

사용자가 확정한 조건은 개발자·신입·서울이다. 아래 세부 정책은 초기 제안값이며 설정에서 변경할 수 있다.

| 항목 | 초기 적용 기준 |
| --- | --- |
| 직무 | 소프트웨어 개발 전반: 프론트엔드, 백엔드, 풀스택, 모바일, 게임, 임베디드, 데이터/AI 개발 등 |
| 경력 | 신입 지원 가능 또는 신입·경력 동시 모집 포함. 경력무관은 별도 배지로 포함 |
| 지역 | 실제 근무지에 서울이 포함된 공고. 회사 본사 주소로 대체 판정하지 않음 |
| 기술 스택 | 아직 제한 없음. 사용 언어만으로 자동 제외하지 않음 |
| 고용형태·학력·연봉 | 아직 제한 없음. 인턴·계약직 여부와 미제공 정보를 표시 |
| 알림 | 목록 조건과 별도 저장. 기본 대상은 신입 지원 명시 공고, 경력무관 알림은 기본 꺼짐. 이메일 및 연결된 카카오톡 묶음 알림 |

‘경력 1년 이상 필수’처럼 신입 지원이 불가능한 공고는 제외한다. ‘신입·경력’ 통합 공고에서 개발 직무에 별도 경력 요건이 있다면 해당 직무 요건을 우선한다. 경력무관이어도 상세 요건에 필수 경력이 있으면 신입 대상에서 제외한다. 상세 정보가 없어 모순을 해소할 수 없으면 ‘지원 조건 확인 필요’로 분리하고 기본 신규 알림에서 제외한다.

지역이 ‘서울·경기’이면 포함하되 복수 근무지임을 표시한다. ‘전국’이나 근무지 미상은 서울 확정으로 판단하지 않고 확인 필요로 분리한다. 서울 근무지가 없는 완전 원격 공고는 현재 기본 조건에서 제외하며 ‘전국 원격 포함’ 옵션을 별도로 제공한다.

직무 코드와 제공된 업무 내용으로 개발 직무 여부를 판단한다. 제목에 ‘개발’이 있어도 사업개발·영업개발이면 제외한다. 교육생 모집·부트캠프 홍보는 채용공고와 구분한다. 개발 직무 판정이 불확실하면 확인 필요로 분리한다.

가상 공고로 보는 기대 결과(실제 채용정보 아님):

| 공고 | 결과 | 이유 |
| --- | --- | --- |
| 서울 마포 / 프론트엔드 / 신입 | 포함·알림 | 세 조건 충족 |
| 서울 강남 / 백엔드 / 경력무관 | 목록 포함·기본 알림 제외 | 경력무관 배지 표시, 별도 알림 선택 가능 |
| 서울 구로 / 게임 개발 / 경력 3년 필수 | 제외 | 신입 지원 불가 |
| 경기 성남 / 서버 개발 / 신입 | 제외 | 서울 근무지 없음 |
| 서울 중구 / 사업개발 / 신입 | 제외 | 소프트웨어 개발 직무 아님 |
| 근무지 미상 / 앱 개발 / 신입 | 확인 필요·알림 제외 | 서울 여부 확인 불가 |

알림 예시(가상): ‘[서울 신입 개발자] 예시회사 · 프론트엔드 개발자 — 서울 마포구 / 신입 / 정규직 / 마감일 및 원문 링크’. 최초 연결 때 기존 공고는 목록에 채우고 이후 발견한 신규 공고부터 알린다.

초기에는 규칙 기반으로 일치 사유를 설명한다. AI 분류는 후속 실험으로 두며 필수 조건을 무시하는 추천이나 낮은 신뢰도의 자동 제외에 사용하지 않는다.

여러 직무를 모집하는 공고는 제공 데이터에서 구분할 수 있을 때 모집 직무별 경력·지역·필수 요건을 저장한다. 예를 들어 ‘영업 신입 / 개발 경력 3년’은 신입 개발 공고에서 제외한다. 부문별 분리가 불가능하면 확인 필요로 처리한다. 희망 기술 스택은 초기에는 관심도에만 사용하고 사용자가 필수 조건으로 지정한 경우에만 제외 판단에 사용한다.

## 5. 수집 파이프라인과 갱신

스케줄러 → 사이트별 수집기 → 원본 검증 → 공통 형식 변환 → 중복 확인 및 저장 → 저장 조건 매칭 → 알림 대기열 → 발송 작업자.

각 수집기는 fetchPage, normalize, healthCheck를 제공한다. 소스별 호출 제한, 페이지 처리, 타임아웃, 재시도, 변경 감지 상태를 독립 관리한다. 인증 오류는 자동 무한 재시도하지 않는다. 429에는 제공자의 재시도 지침과 호출 예산을 적용한다.

사람인은 전체 API 키 기준 하루 500회 이내로 관리한다. 제안 시작값은 15분 간격이며 하루 96회 실행이다. 실행당 요청이 3개면 288회, 5개면 480회이므로 검색 분할·페이지·재시도까지 합산해야 한다. 기본 운영 예산을 400회로 두고 100회를 복구에 예약하되 총한도는 넘지 않는다. 이용자마다 개별 수집하지 않고 겹치는 조건을 합쳐 공용 수집한다. 예산을 넘는 경우 주기를 늘리거나 범위를 줄이고 화면에 반영한다.

잡코리아는 안내된 2시간 갱신에 맞춰 시작한다. 다른 소스는 승인 한도에 따라 설정한다. 전체 지연은 공급자 반영 지연 + 수집 대기 + 처리·발송 지연으로 구분한다. 내부 목표는 정상 상태에서 발견 후 2분 안에 발송 요청하는 것이며 수신 도착을 보장하는 수치는 아니다.

페이지 수집 도중 실패하면 완료 지점을 잃지 않도록 체크포인트를 저장한다. 시간순 조회가 가능하면 겹치는 조회 구간과 ID 중복 제거를 적용하고, 시간 필터가 없으면 페이지 스캔과 주기적 재확인을 사용한다. 모든 페이지를 확인한 뒤에만 수집 구간 완료를 확정한다. 공급자 상한으로 누락 가능성이 있으면 coverage_limited 상태를 표시한다.

사용자에게는 소스별 ‘연결 대기 / 수집 완료 / 일부 수집 / 장애’와 마지막 성공 시각을 함께 표시한다. ‘수집 완료’는 설정한 조건과 제공 API 범위에서의 완료이며 사이트 전체 공고의 완전 수집을 뜻하지 않는다.

## 6. 중복·마감·최초 알림 정책

- 동일 소스 공고는 (source, external_id)로 유일하게 저장한다.
- 여러 사이트의 유사 공고는 ‘유사 공고 묶어보기’로 제공한다. 원본을 삭제하거나 단일 공고로 병합하지 않는다. 유사성 추정만으로 신규 알림을 억제하지 않으며 동일 채용임을 확정할 수 있을 때만 교차 소스 중복 알림을 줄인다.
- 묶인 공고도 원본 링크와 식별자를 모두 유지한다. 수정은 이력으로 기록하고 신규 공고처럼 재발송하지 않는다.
- 최초 연결의 기존 공고는 기본적으로 목록만 채운다. 초기 결과 요약은 사용자가 선택한 경우 발송한다.
- 검색 조건을 바꿔도 기존 공고 전체를 다시 신규 알림으로 보내지 않는다. 규칙 활성화 시 기준시각과 기존 매칭 기준선을 저장한다.
- 소스 명시 상태나 마감일로 마감을 판단한다. 검색 결과에서 한 번 사라졌다는 이유로 마감 처리하지 않는다.
- 수집 장애는 공고 삭제나 마감으로 바꾸지 않고 마지막 확인 시각과 상태 불확실성을 표시한다.

## 7. 이메일과 휴대폰 알림

개인용 카카오톡은 공식 메시지 API의 ‘나에게 보내기’를 첫 검증 대상으로 한다. Google 로그인과 별도로 카카오 계정을 연결하고 필요한 메시지 권한에 동의한다. 본인의 ‘나와의 채팅’으로만 발송하며 임의의 전화번호로 보내는 기능이 아니다. 개발자 앱 설정, 사용 권한, 쿼터와 서비스 목적 적합성을 확인한 뒤 활성화한다. 액세스·리프레시 토큰은 서버에서 암호화 보관하고 갱신 실패 시 재연결 상태로 전환한다.

카카오 메시지 API 성공과 휴대폰 배너·소리 발생은 별개다. 실제 기기에서 앱이 닫힌 상태의 수신과 알림 동작을 먼저 시험한다. 기대한 알림이 발생하지 않으면 이메일을 유지하고 텔레그램 또는 웹 푸시를 대안으로 제안한다. 공개 서비스 확장 시 개인용 연동을 그대로 대량 발송에 사용하지 않고 카카오 권한 심사 또는 비즈메시지 제공 경로를 별도 검토한다.

카카오 공식 자료:
- https://developers.kakao.com/docs/ko/kakaotalk-message/common
- https://developers.kakao.com/docs/ko/kakaotalk-message/rest-api

Google 로그인은 사용자 식별 용도다. Gmail 주소로 알림을 수신하는 데 메일함 읽기 또는 Gmail 발송 권한은 필요 없다. 서비스 발신 도메인을 인증한 이메일 제공업체에서 확인된 수신 주소로 보낸다. 초기 후보는 Resend이며 운영 전 도메인·제공 한도·비용을 확인한다.

웹 푸시는 별도 사용자 권한과 기기별 구독이 필요하다. iPhone은 iOS 16.4 이상 홈 화면 웹앱 등 지원 조건을 안내한다. 권한 거부 또는 지원 불가 시 이메일로 사용할 수 있게 한다. OS·브라우저 설정 때문에 전달이 지연되거나 차단될 수 있다.

알림은 발견 즉시, 묶음, 일일 요약 중 선택한다. 방해금지 시간에는 대기시켰다가 해제 후 묶는다. 기본 시간대는 Asia/Seoul이다. 여러 규칙에 동시에 맞아도 사용자·공고·채널별 신규 알림은 한 번만 생성한다.

초기 제안값은 1시간 묶음 알림이며 해당 시간에 새 결과가 없으면 발송하지 않는다. 세부 개발 분야 미선택 상태에서는 전체 개발 분야를 대상으로 하되 신입 지원 명시 공고만 기본 알림에 포함한다. 경력무관과 관심 분야는 각각 설정할 수 있다. 수집 주기와 묶음 발송 주기는 별개이며 공급자 갱신보다 빠른 발견을 보장하지 않는다.

마감 알림은 선택 활성화 시 기본 D-1 한 번으로 제안한다. 정확한 마감일이 없는 ‘채용 시 마감’은 일자를 추정하지 않는다. 중요 변경은 근무지·필수 경력·고용형태·급여·마감일 변경으로 한정하고 전후 값을 표시한다. 단순 문구 수정은 제외한다. 날짜만 제공된 마감은 시각 미상으로 표시한다. 동일 변경과 마감 일정은 재시도로 중복 알리지 않으며, 발송 직전에 최신 공고 상태·스크랩·수신 설정을 재확인한다.

DB 트랜잭션에서 공고 매칭과 outbox를 함께 저장한다. 발송은 임대 잠금, 재시도 횟수, 다음 시도 시각을 관리하고 지원되는 제공업체에는 멱등성 키를 전달한다. 제공업체 접수 직후 연결이 끊기면 결과를 대조하며 외부 채널의 완전한 exactly-once는 보장하지 않는다. 접수·전달·실패를 구분한다. 만료된 푸시 구독은 해제하고 수신 거부와 계정 삭제는 대기 알림에도 반영한다.

## 8. 권장 기술 구성

| 부분 | 제안 | 선택 이유 |
| --- | --- | --- |
| 웹/PWA | Next.js + TypeScript | PC·모바일 화면과 서버 API를 함께 개발 |
| DB/인증 | Supabase PostgreSQL + Google 로그인 | 관계형 데이터와 사용자별 접근 제어 |
| 수집·알림 | 별도 Node.js TypeScript worker | 화면 요청과 독립적으로 지속 실행 |
| 작업 대기열 | 초기 PostgreSQL outbox | 작은 규모에서 추가 큐 서버를 줄임 |
| 이메일 | Resend 후보 | 발신 도메인 기반 API 발송 |
| 메신저 알림 | 카카오톡 나에게 보내기 우선 검증 | 개인 계정으로 공고 수신 |
| 보조 모바일 알림 | 표준 Web Push 후보 | 메신저 수신 검증 결과에 따라 추가 |
| 검증 | 단위 테스트 + Playwright | 매칭 규칙과 실제 사용자 흐름 확인 |

웹과 worker는 분리 배포할 수 있게 한다. 잡코리아 서버 IP 등록이 필요하면 worker의 고정 송신 IP를 확보한다. 호스팅 사업자는 승인 결과·예산에 따라 결정한다. 로컬 PC에서 수집기를 실행하면 PC가 꺼진 동안 수집이 중단되므로 상시 알림에는 상시 실행 서버가 필요하다.

현재 설계에 추가 Codex 플러그인은 필수 조건이 아니다. 제품의 상시 수집·발송은 애플리케이션 서버가 담당한다. 필요한 것은 승인된 데이터 접근, 로그인 설정, 발신 도메인, 배포 환경이다.

## 9. 데이터와 API 초안

주요 테이블: users, sources, source_jobs, job_groups, job_versions, role_mappings, saved_searches, matches, bookmarks, notification_channels, notification_outbox, notification_deliveries, ingestion_runs, ingestion_cursors.

추가 모델: job_positions(모집 부문별 요건), notification_rules(목록 검색과 독립된 알림 조건), job_feedback(관심 없음 사유), exclusion_rules(명시적 제외 규칙), applications(지원 상태). job_groups는 원본을 유지하는 유사 관계다. 알림 이벤트는 new_job, deadline_reminder, important_change로 구분하고 사용자·원본 공고·채널·이벤트 종류·이벤트 식별자로 중복 생성 방지 키를 구성한다. 변경 이벤트에는 버전, 마감 이벤트에는 대상 마감일을 포함한다.

source_jobs는 원문 ID·URL·게시시각·최초 발견시각·최종 확인시각·마감시각·콘텐츠 해시를 구분한다. 저장 허용 범위에 맞춰 원본 응답과 본문 보관 정책을 설정한다. saved_searches에는 조건 JSON, 매칭 버전, 활성화 기준시각을 저장한다. 구독 정보·이메일·개인 설정은 사용자 소유이며 다른 사용자가 접근하지 못하도록 RLS 및 서버 권한 검증을 적용한다. 서비스 키와 공급자 키는 서버 비밀 저장소에만 둔다.

API 초안: GET /api/jobs, GET/POST /api/searches, PATCH/DELETE /api/searches/:id, POST /api/bookmarks, GET /api/notifications, POST/DELETE /api/push-subscriptions. 운영용 수집 실행은 일반 사용자 API와 분리하고 인증한다. 공고 목록은 커서 페이지네이션을 사용한다.

## 10. 구현 순서와 완료 조건

1. 데이터 확보 가능성 검증: 제공 조건 및 신청 요건 확인 → 승인/키 확보 → 실제 응답과 서울 신입 개발 조건 지원 여부 확인. 키가 없으면 ‘대기’로 기록하며 성공으로 처리하지 않는다.
2. 카카오톡 최소 연동 검증: 계정 연결·나에게 보내기·실제 기기 배너와 소리·토큰 갱신·연결 해제 확인. 기대한 알림이 안 되면 이메일을 유지하고 대안을 비교한다.
3. 샘플 기반 필터 검증: 신입·경력무관·부문별 경력·서울 복수 근무지·사업개발·교육 광고·미상 정보 사례를 기대 결과와 대조한다. 외부 승인 대기 중에도 이 작업을 진행한다.
4. 화면 및 핵심 기능: 목록/알림 조건 분리, 지원 가능성과 관심도, 유사 공고 보기, 피드백과 지원 상태. 샘플 데이터를 명시한다.
5. 수집·이메일·메신저 통합: 페이지/호출 예산/장애 복구, 묶음 알림, 선택형 마감·변경 알림, 수신 거부 검증. 테스트 수신자를 명시적으로 설정한다.
6. 추가 소스 및 운영: 승인된 사이트부터 확장하고 배포·비밀 관리·백업·오류 알림·복구를 확인한다.

필수 검증: 같은 공고 재수집 시 추가 알림 없음, 여러 규칙 중복 일치 시 한 번 발송, 미상 필드 정책 준수, 부분 페이지 실패 복구, 쿼터 초과 방지, 장애 중 허위 마감 방지, 방해금지 시간과 수신 거부 적용, 다른 사용자 데이터 접근 차단.

추가 완료 조건: 목록 설정 변경이 알림 설정에 영향을 주지 않음, 경력무관 기본 알림 제외, 모집 부문별 요건 적용, 유사 공고 원본 보존, 관심 없음 취소 및 규칙 범위 검증, 중요하지 않은 수정 알림 없음, 마감일 변경과 재시도 시 중복 방지. 외부 실연동 결과와 샘플 검증 결과는 따로 기록한다.

확정된 방향은 개인용부터 시작해 서비스로 확장하며 이메일과 메신저를 사용하는 것이다. 사용자 기본 조건은 개발자·신입·서울이다. 세부 개발 분야와 기술 스택은 제한하지 않은 상태이며 운영 예산은 미정이다. 카카오톡의 적합성은 실제 연동으로 검증한다. 제공업체 약정이 확정되기 전에는 수익화·전국 전체 공고 수집·무제한 사용을 제품 전제로 두지 않는다.
